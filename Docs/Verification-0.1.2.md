# 轻看 0.1.2 功能与资源复查

验收日期：2026-10-12。本轮从 0.1.1（`8487f21`）重新运行测试，
检查日常浏览、文件操作、异常输入、多窗口与资源使用。仅操作合成图片、
临时文件和临时偏好，没有修改用户照片。安装未重置用户偏好。

## 已修复的问题

| 问题 | 修复后的行为 |
| --- | --- |
| 小图之外的第二次打开请求被忙加载丢弃 | 只保留最新待打开请求，不并行启动更多主图解码 |
| 外部编辑覆盖了同大小文件，仍显示旧缓存 | 缓存包含修改时间；读取完成后校验大小、时间与色彩目标 |
| 加载期间改颜色设置退回上一张图 | 重读最新请求并使用新的色彩目标 |
| 删除确认写着 A，后台切图完成后可能删 B | 确认绑定文件路径；图片切换后该确认不再执行删除 |
| 撤销删除遇到同名文件时丢失撤销记录 | 恢复失败时保留记录，不打开或覆盖冲突文件，允许重试 |
| 重命名同名冲突可能使错误对话框释放栈对象而崩溃 | 错误框独立管理生命周期；失败后原图/GIF 恢复，无变化时不释放 GIF 设备 |
| 日期、创建时间和大小的升降序与选项相反 | 与界面的升序/降序含义一致 |
| 修改排序后工具栏序号过期 | 更新排序时同步刷新序号 |
| GIF 旋转后点击 100% 或禁用重采样丢失方向 | 各显示路径均使用已经旋转的当前帧 |
| 新建空窗口禁用其他窗口的“打开方式” | 菜单启用状态仅作用于所属窗口 |
| EXIF 方向处理后的图片信息宽高仍颠倒 | 显示自动方向处理后的宽高；SVG 保留固有尺寸 |
| 24 MP 错显示成 24.1 MP | 正确四舍五入，避免重复偏移 |
| 两张图片目录循环时邻图重复解码 | 同一轮与进行中的路径去重 |
| 工具栏对收到的鼠标输入与全局指针不一致时仍隐藏 | 用实际收到的鼠标位置判断悬停，离开、移动窗口或改变几何时使记录失效 |

## 资源策略

- 默认共享解码缓存上限仍为 200 MiB；开启更大的预加载模式才使用 800 MiB。
- 预加载按元数据中的解码尺寸预算，而不是压缩文件大小；单张邻图不超过
  共享缓存预算的一半，所有窗口共用进行中预加载预算。
- 预算保留到读取结果被消费或丢弃。窗口关闭时后台任务仍可安全完成；
  不假称可以取消正在进行的原生解码。
- 关闭最后一个图片窗口清空解码缓存；关闭预加载选项立即清空缓存，
  老代次的迟到结果不能重新填充。
- 跳过 GIF/SVG 的邻图预读，避免其元数据解析在界面线程阻塞。
- Qt 单图解码分配限制从 8 GiB 降至 512 MiB。预算并非整个进程的内存硬上限：
  当前图片、格式转换、显示、临时解码和系统库均有额外开销。

## 常用功能与取舍

新增「文件 → 打开文件夹」和 ⌘⇧O，复用目录自然排序与翻图，不创建图库、
不扫描子目录、没有增加框架或网络依赖。删除已失效的 Open URL 快捷键条目，
避免与新入口的快捷键设置冲突。

已检查打开图片/目录、同文件夹翻图、排序、缩放平移、100%、旋转/镜像、
全屏与 Esc、GIF 播放/暂停/逐帧、幻灯片、文件信息、复制图片与文件地址、
本地文件粘贴、重命名、移到废纸篓与撤销、最近文件、多窗口、设置保存与取消、
损坏/丢失图片后的恢复、中文路径、透明度和大图。

纯截图/位图剪贴板粘贴尚未支持，当前粘贴接受本地文件 URL；自动化验证了
复制时带图片数据和文件地址。缩略图侧栏、RAW/PSD 专用解码、多页文档浏览、
编辑导出仍未新增；本轮优先稳定现有功能和控制资源。HEIC 仍为系统解码到
sRGB 的 SDR 浏览，不承诺 HDR/P3 原始显示范围。

### 关闭窗口后的驻留保留

关闭三个窗口、结束线程池任务、清空解码缓存并回到真正外层 Cocoa 循环后，
footprint 仍约 867 MiB。这是实际观测，不能说关闭后物理内存立即下降。
额外诊断显示 `vmmap` 中约 824.1 MiB 属于 `Malloc Large (empty)`；所有
malloc zones 的存活分配仅约 16.8 MiB，最大存活块 400 KiB，没有存活的
96/192 MB 图片缓冲。普通 `malloc_zone_pressure_relief` 返回 0，未使驻留下降。
原始证据为 `resource-fixed-closing-{vmmap,heap}.txt` 与对应 JSON。

进一步用独立 `tests/allocator_probe.c` 排除 Qt 与图片解码：只 malloc 一个
96,000,000 字节缓冲、逐页触摸并 free。footprint 从 1.17 升至 92.78 MiB，
free 后保持；再分配两次复用了同一个地址，占用稳定在 92.81 MiB。
该机器的系统分配器会保留已释放、可复用的大块内存；这解释了本轮大部分
关闭后保留，不能把该数字当作仍被应用图片对象持有的内存，也不能据此
保证所有输入下都没有泄漏。诊断没有增加全系统压力或修改分配器保护选项。

Apple 的公开实现中，大块释放通过 `mvm_reclaim_mark_free` 标记，后续
`large_malloc_from_cache` 可以复用；本轮产品没有调用私有回收接口或改变
系统分配策略。[Apple libmalloc 大块管理](https://github.com/apple-oss-distributions/libmalloc/blob/main/src/magazine_large.c)，
[Apple libmalloc VM 回收](https://github.com/apple-oss-distributions/libmalloc/blob/main/src/vm.c)。
